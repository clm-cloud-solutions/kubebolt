# KubeBolt 2.7.0 — a cluster being prepared says how far it is, and a large cluster connects

Drop-in over 2.6.4. No schema change, no migration, no chart change, and the
agent stays on **1.4.9**.

## A cluster being prepared says how far it is

Before KubeBolt can serve a cluster's views it loads the cluster into memory:
every object its role can read, one LIST per kind. On a small cluster that
takes a second. On a large one behind a slow link it took minutes, and all the
page showed was a spinner.

The page now says what is happening and why:

- **The steps.** Agents connected, access checked (how many kinds the role
  may read, and which ones it may not), loading the cluster, first health
  check.
- **How far it is.** A bar that follows the data still to arrive, measured
  from the API server's own count of the objects left in each LIST, with an
  estimate of the time left once the rate is known.
- **What has arrived.** The kinds loaded, the data received and its rate, the
  elapsed time, and an Activity log of each step as it happens.
- **The cluster's CPU and memory.** The agents ship metrics before the cache
  has synced, so an agent-connected cluster shows them while it loads.
- **What travels.** The objects KubeBolt's role can read, through the agent's
  outbound channel or with the kubeconfig context's credentials. They stay in
  KubeBolt's memory; Secret values are never displayed, and revealing one takes
  an editor and is audited.

When it shows: a cluster's first connect, after KubeBolt restarts or is
upgraded, when a failed connect is tried again, and when a cluster KubeBolt had
let go is opened again (its agents left, or a kubeconfig cluster was idle for
30 minutes or beyond the 8 held at once). Moving between pages, refreshing, or
switching to a cluster KubeBolt already holds stays instant, without it.

Nothing about what the API serves changes: the cluster's views still open
together once it is ready. The page reads the new `GET /clusters/progress`,
which never starts or waits for a connect.

During a switch the menu no longer shows the previous cluster's counts, and the
state pill says *Connecting* instead of *Disconnected*.

## A large cluster connects behind a slow agent tunnel

On a cluster with thousands of workloads, the first connect sends tens of MB
through the agent. At under 1 MB/s that does not fit a fixed deadline, and the
connect failed at the same point on every attempt while pages were still
arriving.

- **Timeouts measure silence, not duration.** The connect and cache-sync
  timeouts (`KUBEBOLT_AGENT_PROXY_CONNECT_TIMEOUT`,
  `KUBEBOLT_CACHE_SYNC_TIMEOUT_SECONDS` and their settings) now fail a connect
  when nothing arrives from the cluster for that long. A connect that keeps
  receiving pages carries on, up to 10 minutes. A stuck agent still fails at
  the same point.
- **A failed connect is not restarted by every request.** While a connect kept
  failing, every request for the cluster (the UI polls every few seconds)
  started another full connect, each one restarting the initial LIST through
  the agent. After a failed attempt, requests now wait 30 seconds, then 1, 2
  and 4 minutes, at most 5, and say when the next attempt is. An agent
  reconnecting and an explicit switch to the cluster still try at once.
- **No guessed namespaces.** When a kind was denied cluster-wide, the
  permission probe listed namespaces to look for namespace-level access, and on
  any error fell back to `default`, `kube-system` and `kube-public` without
  saying so. Through a slow tunnel the cluster could connect with some kinds
  served from two namespaces: lists that looked complete and were not. The
  namespace LIST is now retried; if it keeps failing, those kinds stay without
  access and the views say so. The common namespaces are tried only when the
  ServiceAccount may not list namespaces at all.
- **Every failed attempt is logged** (`cluster runtime failed to connect`, with
  the reason). The background path used to drop the error.

## Helm's release history stays in the cluster until a view needs it

Helm stores every revision of every release as a Secret holding the whole
release: chart, values and every rendered manifest. KubeBolt downloaded all of
it at every connect and listed it again every minute, payload included, for
the insights and for the Overview and Applications views.

- The Secrets cache leaves Helm's storage out. Lists and counts read its
  metadata, once a minute.
- A release's payload is read when something needs it: its latest revision,
  once, for the Applications list or for an insight about a failed or stuck
  release. The release detail reads only that release.
- The Secrets list, a storage Secret's detail and the Overview's counts still
  show them.

On a test cluster with 10 releases, Secrets went from 7.1 MiB to 12 KiB a
minute through the agent tunnel with the Overview open, and a loaded
Applications list answers in under a millisecond (it took about 140 ms).

A release's *History* tab also spaces its columns and wraps a long
description, such as a failed upgrade's error.

## Onboarding and agents

- **A wizard's agent token stops working if no agent uses it within a week.**
  The onboarding and the add-cluster wizard issue a token on every attempt,
  and none expired: each abandoned attempt left a working ingest credential. A
  token those wizards hand over to copy now stops working after 7 days unless
  an agent uses it first; once one has, it keeps working. The wizards say until
  when, and Agents › Tokens shows it. A token the API writes straight into the
  cluster's Secret (install, configure) has no such window.
- **Advanced setup has a way back.** Opened from the onboarding, it reuses the
  onboarding's token and name instead of issuing a second token, and has *Back
  to the simple setup*.
- **An agent short of memory says so, with the command that fixes it.** When an
  agent pod is OOMKilled or stays near its memory limit, the *OOMKilled* and
  *Memory Near Limit* insights give the `helm upgrade` that raises it (twice the
  current limit, at least 256Mi), pinned to the chart version the agent runs.
- **Documentation links open kubebolt.io.** The integration catalog, Cost,
  Reliability and the add-cluster wizard opened guides in the GitHub
  repository. The Prometheus remote_write cards keep the repository guide for
  now.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt \
  --version 2.7.0 -n kubebolt --reset-then-reuse-values
```

Use the namespace you installed into: `helm list -A | grep kubebolt` shows it.
`--reset-then-reuse-values` needs Helm 3.14+; passing your values file (`-f`)
works too. Do not use `--reuse-values`: it keeps the previous chart's defaults,
pinned image tags included. Step by step, what to expect, rollback, and what
each version asks of you when you skip some:
[Upgrade](https://github.com/clm-cloud-solutions/kubebolt/blob/main/deploy/helm/kubebolt/README.md#upgrade).

Nothing in 2.7.0 asks anything of you. If you raised the connect or cache-sync
timeout to get a large cluster connected, you can return it to its default:
a connect that keeps receiving pages is no longer cut by it.

The agent stays on 1.4.9: there is no agent release with 2.7.0. The next one
raises the agent's default limits to 256Mi / 500m and answers a response too
large for its memory with an error instead of being OOMKilled. Until then, on a
cluster with thousands of workloads, raise the limit on the agent's release
with `--set resources.limits.memory=512Mi`, or follow the command the
*OOMKilled* insight gives.
