# KubeBolt 2.7.3 — the WebSocket token leaves the URL, and a finished pod is not a warning

Drop-in over 2.7.2. No schema change and no migration. The agent stays on
**1.4.10**; there is nothing to upgrade in your clusters.

## The WebSocket access token leaves the URL

A browser cannot set an `Authorization` header on a WebSocket upgrade, so the
web put the access token in the URL of `/api/v1/ws` (live updates) and
`/ws/exec` (the pod terminal). A URL ends up in places nobody meant to keep a
credential: a proxy's access log, the browser history, a support screenshot.

- The web now sends the token as a subprotocol,
  `base64url.bearer.kubebolt.io.…`, next to `kubebolt.v1`. This is how the
  Kubernetes API server authenticates WebSockets.
- The server selects `kubebolt.v1`, so the token is never echoed back.
- `?token=` is still accepted for web bundles cached before this release, with
  a one-time warning in the log. It will be removed in a later release.

If a proxy in front of KubeBolt filters WebSocket headers, it must let
`Sec-WebSocket-Protocol` through. nginx and Envoy pass it by default.

## A connected cluster says how long it has been connected

For a cluster whose agent is connected, `lastSeen` carried the time the agent
registered. A cluster reporting right now read "live 2d" in Fleet, and a model
reading `list_clusters` took it for a cluster last seen two days ago.

- **`GET /clusters` returns `connectedSince` for a connected cluster, and
  `lastSeen` only for one that is not.** If you read `lastSeen` from the API,
  read `connectedSince` for connected clusters.
- Fleet reads "live · connected 2d".

## A finished pod is not a warning

A pod in phase `Succeeded` finished its work. A Job's pods end that way, and so
does a long-running pod a node shutdown stopped cleanly: its ReplicaSet leaves
it behind, and nothing deletes it while its node exists.

- The Overview's namespace tiles counted it as not ready, turning a healthy
  namespace amber, or red when such pods outnumbered the live ones. It is now
  counted apart and drawn neutral in the bar; the tile still counts every pod,
  and its tooltip says how many completed.
- Its READY `0/1` in the pod list is neutral instead of amber.
- A `Failed` pod still counts as not ready: that one is worth a look.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt \
  --version 2.7.3 -n kubebolt --reset-then-reuse-values
```

Use the namespace you installed into (`helm list -A | grep kubebolt`).
`--reset-then-reuse-values` needs Helm 3.14+; passing your values file (`-f`)
works too. Do not use `--reuse-values`: Helm keeps the previous chart's
values, defaults included, so the chart's pinned image tags stay old. Step by
step, rollback, and what each version asks when you skip some:
[Upgrade](https://github.com/clm-cloud-solutions/kubebolt/blob/main/deploy/helm/kubebolt/README.md#upgrade).

This version asks nothing of an upgrade from 2.7.2. During the rollout, a page
from the new web that reaches the old API cannot open its WebSocket; it
reconnects on its own once the new API answers.
