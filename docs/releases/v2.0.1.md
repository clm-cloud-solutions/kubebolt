# KubeBolt 2.0.1 — the self-monitored cluster stops being a second-class citizen

Drop-in over 2.0.0. No schema change, no migration, no agent bump, no new
configuration surface. Homologates **EE 2.0.1-e2**.

Small release, and two of its three changes share one root: code that assumed a
cluster reaches KubeBolt through an **agent**. The cluster KubeBolt runs *inside*
— or any context read straight from a kubeconfig — does not, and the places that
assumed otherwise degraded quietly rather than failing.

| | Impact |
|---|---|
| **Finding detail claimed "cluster not connected"** | every security finding on a directly-connected cluster (in-cluster or kubeconfig), about a cluster that was live and serving |
| **Provider icons were grey, and local clusters drew a cloud** | cosmetic, plus a branch that never fired |
| **One Trivy waiver file for two different problems** | a vendor's unfixable CVE could have silenced one in code we compile |

## 1. A stored UID is not a context name

Two identities travel through the system and they are not interchangeable. A
persisted record carries the **kube-system UID** — the canonical id for agent
samples, `ClusterInfo` and the Falco ingest. Runtime resolution keys on the
**context name**, which for an agent-backed cluster is `agent:<uid>` and for a
direct one is `in-cluster` or the kubeconfig entry's name.

`ContextNameForClusterID` crosses that seam, and only ever looked in the
agent-proxy map. A direct context is not in that map; its UID lives only in the
persisted `cluster_uid` bucket. So the function returned the UID unchanged, and
downstream that does not fail — it **lies**: no runtime answers to a name shaped
like a UID, so the finding-detail panel concluded the cluster was down and
rendered a stored-only view with a warning, for a cluster that was serving.

The resolver now reads the persisted map as its second path (the manager lock is
released before the store call), the panel passes the resolved name as the
routing key, and the warning text is terminated as a sentence so a backend error
no longer runs into the copy that follows it. Three tests pin the behaviour,
including the deliberate one: an unknown UID still comes back unchanged (its
callers disagree about that, and changing it is a separate commit).

## 2. Official provider logos

Cluster cards showed a grey glyph for every cloud, three of them drawn by hand.
They now carry the official mark in the brand's own colour (Simple Icons, CC0,
plus the four full-colour symbols that exist). Four tiers: full colour (Google
Cloud, Azure, DigitalOcean, OpenStack); colour on light and monochrome on dark
(AWS — its wordmark vanishes on the dark panel); monochrome glyph in the brand
colour (the other fifteen); a generic cloud when no glyph is published.

**A live bug went with it.** The backend emits the friendly name (`kind (local)`,
`Oracle Cloud`), not the providerID scheme, and the component compared against
`'kind'` — a local cluster missed its branch and drew a cloud. Provider names now
normalise to a canonical key first. Linode draws Akamai's mark; local clusters
stay a neutral server on purpose.

## 3. Two Trivy waiver files

Until now one `.trivyignore` was passed both to the third-party preflight
(VictoriaMetrics, vmagent) and to the scan of the images KubeBolt builds (api,
web, single-container). Waiving a vendor's unfixable Go stdlib CVE would have
muted the same CVE in a binary we *can* fix by bumping the toolchain.

| File | Used by | Rule |
|---|---|---|
| `.trivyignore` | `image-scan` — our images | stays **empty of entries**; bump the dependency instead |
| `.trivyignore-thirdparty` | `preflight-third-party-scan` in `release.yml` **and** `pr-image-scan.yml` | the 8 VictoriaMetrics / vmagent waivers from 1.23.2, owner + exposure + **remove-by 2026-09-15** |

The VM pin does not move: `v1.148.0-scratch` and the newer `v1.149.0-scratch`
are both built with Go 1.26.5 and carry the same set. When it moves,
`deploy/helm/kubebolt/values.yaml` and `deploy/docker-compose.yml` move together
or the preflight's drift check fails by design.

## 4. Go 1.26.6

Already the toolchain on every OSS build path since 1.23.2 (`go.mod` ×3, CI,
CodeQL, the release binaries, the Dockerfiles). Nothing to change; the built
api image scans clean.
