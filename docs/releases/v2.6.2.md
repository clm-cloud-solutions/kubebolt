# KubeBolt 2.6.2 — right-sizing on a cluster's first day, and Kobi says which role a connector needs

Drop-in over 2.6.1. No schema change and no migration, and the agent stays on
**1.4.9**. Nothing to do before upgrading: right-sizing keeps its 48-hour
minimum until an admin lowers it.

## Right-sizing's minimum history is a setting

Right-sizing recommended nothing until a cluster had two days of usage history.
A cluster connected for a trial or a proof of concept therefore showed "collecting
samples" on its first day, exactly when someone was looking at it.

The minimum is now set in **Settings › General › Right-sizing**:

- 48 hours by default, the same as before;
- any value from 12 to 168 hours;
- it applies to every cluster and to Kobi;
- it applies on the next read, with no restart.

Recommendations made from less than 48 hours of history are marked as an
**early estimate**. The panel shows how much history they rest on, for example
"based on 1 day 20h of agent samples · P95 · early estimate". A tooltip explains
that the P95 has not seen two daily peaks yet. Kobi says the same next to its
numbers.

Every "collecting samples" text now names the configured minimum in days and
hours ("needs 2 days", "12h of 1 day 12h collected"), not a fixed "~2 days".

## Kobi says which role a cloud connector needs

A person below a connector's minimum role (*Who can use it in Kobi*, editors and
admins by default) gets no cloud tools. Until now Kobi answered them as if there
were no connector at all.

Kobi now knows which connectors are out of the person's reach and which role
each one needs. When an answer needs those cloud resources, it says so: the
connector, the role, and that an admin can raise the person's role or open the
connector to everyone (Administration › AI (Kobi) › Connectors, *Who can use it
in Kobi*). Then it goes on with the evidence it can read.

## No more burst of 401s every 15 minutes

The access token was renewed only after it had expired. Every 15 minutes, the
next requests in an open tab answered `401 {"error":"invalid or expired token"}`,
then a refresh, then a retry that succeeded. Nothing failed, but DevTools showed
a column of red rows. A message sent to Kobi in that window showed the 401,
because its chat builds its own request and never retried.

The token is now renewed a minute before it expires, Kobi's chat included. The
401 → refresh → retry path stays for what renewal cannot foresee.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt \
  --version 2.6.2 -n kubebolt --reset-then-reuse-values
```

Use the namespace you installed into: `helm list -A | grep kubebolt` shows it.
`--reset-then-reuse-values` needs Helm 3.14+; passing your values file (`-f`)
works too. Do not use `--reuse-values`: it keeps the previous chart's defaults,
pinned image tags included. Step by step, what to expect, rollback, and what
each version asks of you when you skip some:
[Upgrade](https://github.com/clm-cloud-solutions/kubebolt/blob/main/deploy/helm/kubebolt/README.md#upgrade).

The agent stays on 1.4.9: there is no agent release with 2.6.2.
