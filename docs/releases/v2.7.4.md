# KubeBolt 2.7.4 — VictoriaMetrics 1.157.0, on a Go without CVE-2026-97054

Drop-in over 2.7.3. No schema change and no migration. Agent **1.4.11** only
moves its vmagent sidecar to the same release: clusters that do not run the
scrape sidecar have nothing to upgrade.

## VictoriaMetrics and vmagent v1.157.0

The bundled VictoriaMetrics (`metrics.storage.embedded.image.tag` and the
`victoriametrics` service in `deploy/docker-compose.yml`) and the agent
chart's vmagent (`scrape.image.tag`) move from v1.156.0-scratch to
v1.157.0-scratch.

- v1.156.0 was built on Go 1.27.3 and carried CVE-2026-97054 (`net/http`: an
  HTTP/1 server could read past `MaxBytesReader`'s limit; HIGH). v1.157.0 is
  built on Go 1.27.4, which fixes it.
- KubeBolt's own binaries moved to a fixed Go (1.26.11) in an earlier
  release, when no VictoriaMetrics release had one yet, so the CVE was waived
  in `.trivyignore-thirdparty` until 2026-12-03. The waiver is gone, and the
  file has no entries.
- The bundled VictoriaMetrics runs as a ClusterIP Service that only the API
  calls, and vmagent pushes to KubeBolt from inside the cluster: neither was
  reachable from outside.

## Agent 1.4.11

The same agent as 1.4.10, with the new vmagent pin. vmagent runs only with
`scrape.enabled=true`.

- **With the scrape sidecar on**, upgrade the agent chart to 1.4.11, or set
  `scrape.image.tag=v1.157.0-scratch` on 1.4.10.
- **Without it**, 1.4.11 changes nothing in your cluster. KubeBolt lists it as
  the latest agent, so the cluster reads *update available*; there is no
  reason to upgrade now.

## Upgrading

```bash
# The backend
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt \
  --version 2.7.4 -n kubebolt --reset-then-reuse-values

# The agent, in the clusters that run the scrape sidecar (with that cluster's kubectl context)
helm upgrade kubebolt-agent oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt-agent \
  --version 1.4.11 -n kubebolt-system --reset-then-reuse-values
```

Use the namespaces you installed into: `helm list -A | grep kubebolt` shows
them. `--reset-then-reuse-values` needs Helm 3.14+; passing your values file
(`-f`) works too. Do not use `--reuse-values`: Helm keeps the previous chart's
values, defaults included, so the chart's pinned image tags stay old, and
VictoriaMetrics with them. Step by step, rollback, and what each version asks
when you skip some:
[Upgrade](https://github.com/clm-cloud-solutions/kubebolt/blob/main/deploy/helm/kubebolt/README.md#upgrade).

With Docker Compose, pull and recreate the store:
`docker compose pull victoriametrics && docker compose up -d victoriametrics`.

The bundled VictoriaMetrics restarts on the new image and keeps its volume.
Agent batches the API could not write while it restarted are held and written
again once it answers. A VictoriaMetrics you run yourself: move it to v1.157.0
on your own schedule; KubeBolt needs nothing new from it.

This version asks nothing else of an upgrade from 2.7.3.
