# KubeBolt 2.0.4 — a cluster that ingested everything and showed nothing

Drop-in over 2.0.3. No schema change, no migration, no agent bump, no new
configuration surface. The web bundle and the API both change; either can be
deployed first.

| | Impact |
|---|---|
| **A new cluster showed no metrics at all** | samples arriving in VictoriaMetrics, every chart empty and the Coverage bar dark, cleared only by restarting the API |
| **A blip logged the operator out** | any non-401 failure of `/auth/me` cleared the session, and it fires on every tab focus |
| **"Install OpenCost for me" produced a crash loop** | the bundled OpenCost pointed at a Prometheus that does not exist on most clusters and exited on boot |
| **A capability-less agent could still erase a cluster's identity** | the context → cluster_id mapping was deleted on demotion; it is identity, not capability |

## 1. A new cluster showed no metrics at all

Every VictoriaMetrics query is scoped by the cluster's `kube-system` UID. That
UID was read exactly once, in the milliseconds after an agent registered. Lose
that read and the cluster is blind — samples arriving, every chart empty, the
Coverage bar dark — until somebody restarts the API. It lost that read more
often than anyone realised, for three independent reasons.

**It was dispatched to a pod that cannot answer.** `GetProxyAgent` fell back to
*any* connected agent when none advertised `kube-proxy`. That fallback exists
for pre-1.13 agents, which predate capability declaration — but a Mode C
promread pod *does* declare its capabilities, `["metrics"]`, and was picked
anyway; it ignores `KubeProxyRequest` by design, so the caller waited out its
full 15-second deadline. Declaring your capabilities and omitting `kube-proxy`
is saying you cannot proxy; the fallback now applies only to agents that
declared nothing. Measured: 15 s → 3 ms.

**The read was never retried.** It is now, on backoff, for the connector's
lifetime — starting only if the first attempt failed, stopping the moment it
succeeds, with deliberately no overall budget: a deadline just moves the cliff.

**And it was queueing behind our own informers.** The failure was `client rate
limiter Wait returned an error`, not the tunnel: the agent-proxy `rest.Config`
sets only Host and Transport, so client-go applies QPS 5 / Burst 10 to one
bucket shared by ~26 informers. The UID read now has its own small bucket, the
same carve-out the permission probe got in 2.0.3. Isolation, not headroom.

## 2. A blip logged the operator out

`refreshUser` cleared the token and the user on **any** exception from
`/auth/me`, and it runs on every tab focus. A 503 while a cluster was
mid-reconnect, a 5xx, a second of network — all indistinguishable from expired
credentials, and one blip bounced the operator to `/login`. Only a definitive
401 ends the session now (definitive because `fetchWithAuth` has already tried
a silent refresh and retried once); everything else keeps the session and logs
a warning.

## 3. "Install OpenCost for me" produced a crash loop

The wizard emitted `opencost.enabled=true` and nothing else, so the bundled
sub-chart fell back to the official chart's default — `prometheus-server` in
namespace `prometheus-system` — and on any cluster without that exact service
the pod died on boot (`FTL Failed to create Prometheus data source: … no such
host`). The wizard now asks for the Prometheus URL and derives the chart branch
from it: `.svc` as the third label means an in-cluster Service, anything else
is an external URL. It asks **once** — when the metrics source is already
promRead that URL is reused. The agent scrapes OpenCost's `/metrics` directly;
installing OpenCost does not require promRead.

## 4. Identity is not capability

`agentProxyContexts` answers "which cluster is this context" and no longer gets
deleted when an agent without `kube-proxy` registers: a demotion is expressed by
the metrics-only entry alone.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt --version 2.0.4
```

Nothing to migrate.
