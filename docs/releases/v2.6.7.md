# KubeBolt 2.6.7 — a slow agent tunnel connects, and the terminal and the audit trail say what happened

A fix release over 2.6.6. There is no migration, and the agent stays on
**1.4.9**. One default moves: the agent-proxy connect deadline goes from 25s to
60s (see Upgrading).

## A large cluster behind a slow tunnel connects

The first connect to a cluster through its agent lists every resource type
through the tunnel. The connect deadline counts from the last response, and a
single proxied request may take up to the request timeout (30s). The deadline
defaulted to 25s, so one slow page was enough to fail the connect of a large
cluster, and the stuck-agent watchdog could fire the same way.

- The connect deadline now defaults to **60s**.
- Neither the connect deadline nor the stuck-agent watchdog is ever applied
  below the request timeout + 5s, whatever is configured. A value set lower is
  raised, the API logs the raise, and Settings › Agents & Ingest says which
  value runs.

## The terminal says why a cluster refused it

On a cluster whose agent runs in **reader** mode (the chart's default), the
API server refuses `pods/exec`. The agent forwards that answer unchanged, but
the tunnel replaced it with `agent-proxy SPDY: expected 101 Switching
Protocols, got 403`, and the terminal printed that line.

The tunnel now returns the API server's own answer, as client-go does for a
direct connection, and the terminal explains it:

- **Through an agent:** reader mode only reads, and installing the agent with
  `rbac.mode=operator` opens a terminal.
- **Through a kubeconfig:** the credentials of that context may not exec.

The pod file browser and port-forward go through the same tunnel and now get
the API server's reason too.

## The audit trail says what happened

- **A change is recorded against the cluster it was made on.** Cluster
  mutations and the cluster-scoped administration routes (integration install,
  configure, uninstall) took their cluster from a background context, which
  is the install's default cluster, not always the one the request acted on.
  - The record now carries the cluster the request resolved.
  - A mute records the cluster it silences.
  - An unmute, and an access the handler could not tie to a cluster, record
    none rather than the default one.

  Records written before 2.6.7 are not changed.
- **A terminal the cluster refuses is not recorded as opened.** The terminal's
  open record was written as soon as the browser connected, before the exec
  stream was negotiated, so a refused exec (a pod that was gone, or a
  forbidden exec) read as a successful session.
  - The open is now written when the stream runs.
  - A refused stream leaves a single open record with `result: error` and the
    cluster's reason.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt \
  --version 2.6.7 -n kubebolt --reset-then-reuse-values
```

Use the namespace you installed into; `helm list -A | grep kubebolt` shows it.
`--reset-then-reuse-values` needs Helm 3.14+. Passing your values file (`-f`)
works too. Do not use `--reuse-values`: it keeps the previous chart's defaults,
pinned image tags included. For step-by-step instructions, what to expect,
rollback, and what each version asks of you when you skip versions, see
[Upgrade](https://github.com/clm-cloud-solutions/kubebolt/blob/main/deploy/helm/kubebolt/README.md#upgrade).

If you set `KUBEBOLT_AGENT_PROXY_CONNECT_TIMEOUT` or
`KUBEBOLT_AGENT_PROXY_STUCK_TIMEOUT` (or the same fields in Settings) below the
request timeout + 5s, the API now raises it and logs a warning. Raise it in
your values to silence the warning.

To open a terminal on a cluster connected through an agent, that cluster's
agent needs `rbac.mode=operator`.

The agent stays on 1.4.9: there is no agent release with 2.6.7.
