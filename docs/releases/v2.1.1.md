# KubeBolt 2.1.1 — security data follows the cluster out

Drop-in over 2.1.0. No schema change, no migration, no new configuration. The
agent does not need to move for this release; its own gRPC bump ships with the
next agent release.

| | Impact |
|---|---|
| **A removed cluster kept its findings** | Security & Compliance showed a deleted cluster's CVEs, misconfigurations and runtime events indefinitely |
| **Deleting the cluster you were viewing froze the page** | the Overview kept asking for a cluster that no longer existed |
| **gRPC-Go carried two HIGH CVEs** | CVE-2026-84304, CVE-2026-84445 in the API, the agent and the proto module |
| **VictoriaMetrics shipped behind the Go security line** | eight Go stdlib CVEs in the bundled VM and vmagent, held under dated waivers since August |

## 1. Findings follow the cluster when it leaves

The rule the Security pages now honour: a cluster that is registered but merely
**disconnected** keeps its history — Security must answer for a cluster that is
down, that is the whole point of storing findings — but a cluster **removed
from KubeBolt** shows nothing.

Before this release, three independent mechanisms made a removed cluster's
findings immortal:

- the findings sweeper visits **live connectors** only, so a removed cluster's
  active findings were never reconciled to resolved;
- the retention pass deletes **resolved** rows only, never active ones;
- the read path had nothing else that would drop them.

Every admin kept seeing the last sweep of a cluster that was gone, frozen in
time, with no way to clear it short of editing the database.

**Deletion cascade.** Removing a cluster — an agent-proxy cluster or an
uploaded kubeconfig context — now purges its stored findings **and** runtime
events. A row can carry either of two identities (the cluster's kube-system UID,
or its context name while the UID had not resolved yet), so the purge runs
under both. The delete dialog says it before you confirm: *"including its stored
security findings and runtime events"*.

**Orphan sweep.** The hourly retention pass now also removes security data whose
cluster is registered **nowhere** — rows left behind by a delete that happened
before this release. It keys on **membership, not age**: the keep-set is every
identifier a registered cluster can hold data under (UIDs, context names, stored
kubeconfig contexts, the in-cluster identity), and anything outside it goes,
whatever its date. It fails closed: if the cluster registry cannot be read, the
sweep is skipped rather than guessed at — over-keeping is safe, over-deleting is
not. Each pass logs `security_orphans_removed`; expect a one-time sweep of any
historical orphans on the first pass after the upgrade.

## 2. Deleting the cluster you are viewing

Deleting the active cluster used to leave the page on a 503-ing Overview: every
request still pointed at a cluster that had just been removed. It now re-lands
the way sign-in does — on the next live cluster, through the normal switch (the
"Connecting" overlay, a fresh Kobi transcript, that cluster's Overview) — or on
Home when no cluster remains.

## 3. Display fixes found while testing the above

- **Security tables key their rows by cluster.** The same workload name (a
  ClusterRole, an unnamespaced check) or the same fingerprint legitimately exists
  in two clusters; keying rows by name alone produced duplicate keys that
  cross-rendered data between clusters when the scope changed.
- **Fleet says "Agent offline"** for a registered cluster whose agent is down,
  instead of "Reporting".
- **The finding drill-down names the cluster** in its error text — "*dev* is not
  reachable right now — showing the stored finding only" — instead of the
  internal `<uid>.agent.local` URL and a UUID nobody recognises.

## 4. Security

**gRPC-Go 1.83.1 → 1.83.2** (CVE-2026-84304, CVE-2026-84445), with
`golang.org/x/net` 0.58.0, in `apps/api`, `packages/agent` and `packages/proto`.
The API and single-container images pick it up in this release; the agent image
picks it up in its next `agent-v` release.

**VictoriaMetrics and vmagent v1.148.0 → v1.153.0.** The bundled metrics store
and the agent's scraper were built on Go 1.26.5 and carried eight Go standard
library CVEs (`net/http` unencrypted HTTP/2, `html/template`, `encoding/asn1`,
`encoding/xml`, `net/url`, `crypto/tls`, and two in `x/net`). They sat under
dated waivers because there was no upstream rebuild to move to; v1.153.0 is
built on Go 1.27.1 and scans clean, so the waivers are gone and
`.trivyignore-thirdparty` has no entries. The pin moves together in the
`kubebolt` chart, the `kubebolt-agent` chart (vmagent) and Docker Compose.
The storage format is compatible: v1.153.0 opens data written by earlier 1.14x
releases in place, with no migration step.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt --version 2.1.1
```

Nothing to migrate: the upgrade restarts VictoriaMetrics on v1.153.0 over the
same volume. Deleting a cluster now also deletes its stored security
data; a reconnecting agent repopulates it on the next sweep, exactly as after a
disconnect.

## Verification

On kind: connect a cluster with Trivy Operator, let the sweep store findings,
delete the cluster from Clusters and check that Security & Compliance no longer
lists them. Delete the cluster you are viewing and check that the page lands on
another cluster, or on Home when it was the last one.
