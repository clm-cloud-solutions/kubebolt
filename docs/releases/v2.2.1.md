# KubeBolt 2.2.1 — a cluster map you can read at any replica count

Drop-in over 2.2.0. No schema change, no migration, no new configuration. The
agent stays on 1.4.1.

| | Impact |
|---|---|
| **One busy workload made the map unreadable** | a Deployment with 10 pods drew 10 pod cards and a ReplicaSet card per old revision; the namespace block grows with its tallest column, so a few hundred replicas forced the map down to ~3 % zoom |
| **A crash-looping pod showed green** | the map coloured pods by phase, and a pod in CrashLoopBackOff is still phase Running |
| **Finished work cluttered the map** | retired ReplicaSets and completed Jobs, with their pods, were drawn as if they were live |
| **The first-run wizard's agent command could not install** | it omitted `backendUrl` and passed token flags the chart does not have |

## 1. Replicas are grouped

Healthy pods of the same owner — a ReplicaSet, DaemonSet or Job — are drawn as
**one node with a ×N badge**, a stacked edge and one status dot per replica
(up to 36, then "+N"). Edges follow their pods into the group and are
deduplicated: ten `selects` from a Service become one.

What is never grouped, because grouping would hide what you opened the map to
find:

- **Unhealthy pods** stay on their own, showing the reason (`CrashLoopBackOff`,
  `ImagePullBackOff`, …) instead of the phase.
- **StatefulSet pods** and **pods behind a headless Service**: there is no load
  balancer in front, `redis-0` is not `redis-1`, the pod is the endpoint.

A click on a group opens it into its pods. The panel's new **Workloads** section
switches *Grouped / One per pod* and offers *Regroup*; the choice is remembered.

## 2. Traffic reads per workload

The Traffic layout groups too. Each Hubble flow is routed onto its pod's group
and summed per hop, so the view reads *caller → Service → workload ×N* with one
line per hop instead of one per replica. Open a group to see how a Service
spreads its load across the replicas.

## 3. History is hidden by default

In Grid and Flow, retired ReplicaSets (scaled to `0/0`, kept only for rollback)
and completed Jobs with their pods are no longer drawn. A rollout in progress
still shows its old ReplicaSet, because it still has pods, and a **failed** Job
stays, because it is a signal. *History shown* in the Workloads section brings
the rest back. The Deployment's History tab and the CronJob's Jobs remain the
places to read them.

## 4. The first-run wizard installs the agent

The setup wizard's **Agent** step printed a `helm install` that failed: no
`backendUrl`, and with a token it set `auth.ingestTokenSecret`, a key the chart
does not have. The command now takes `backendUrl` from the agent-ingest Service
the backend discovers (in-cluster: the cluster DNS name; outside a cluster: the
discovered endpoint or a visible `<kubebolt-host>:9090` placeholder), uses the
chart's own token keys (`auth.mode=ingest-token`,
`auth.ingestToken.existingSecret`), and carries a permission tier
(`rbac.mode`: metrics / reader / operator) chosen with the same picker as *Add
cluster*. The *Add cluster* "In-cluster backend" preset pointed at the web
Service; it now points at `kubebolt-agent-ingest.kubebolt.svc.cluster.local:9090`.

## 5. Smaller things

- Off-screen nodes are no longer mounted on the canvas.
- Topology Pod nodes carry `metadata.ready` and `metadata.reason`, and headless
  Services `metadata.headless`, for anything else that reads `GET /topology`.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt --version 2.2.1
```

Do not use `--reuse-values` across chart versions; pass your values file
(`-f`) or `--reset-then-reuse-values`.
