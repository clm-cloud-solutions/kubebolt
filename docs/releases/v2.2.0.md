# KubeBolt 2.2.0 — Kobi reads the whole product

API + web, plus **kubebolt-agent 1.4.1** (security patch, same metric schema).
No migration: API tokens gain an optional `clusters` field inside their
existing BoltDB record, and a token without it reads every cluster, as before.

The theme: Kobi — in the chat and through the MCP server your own LLM client
connects to — could read the cluster's live objects and little else. The
product already knew about security findings, insight history, bursts, deploys,
coverage, metrics and right-sizing, and Kobi answered "I can't see that". Now it
reads all of it, the answers stay inside the clusters the caller may read, and
an MCP token says which clusters those are.

| | Impact |
|---|---|
| **Kobi could not see most of the product** | findings, runtime events, insight history, bursts, deploys, coverage, PromQL, right-sizing — now tools |
| **An MCP token was all or nothing** | "MCP only" keys, and a per-token cluster list enforced on every read |
| **Caller-written PromQL could escape its cluster** | now confined by the metrics store itself |
| **List results were shaped for the screen** | 14 pods came to 41 KB and were cut; Kobi miscounted |
| **The chat's cost was mostly cache writes** | the static prompt stays cached for an hour |

## 1. Kobi reads the rest of the product

Every tool below is read-only, available in the chat and on `/api/v1/mcp`, and
answers for clusters that are down where the data is stored rather than live.

**Security & Compliance.**
- `get_findings` — the posture (counts by severity, source and kind, the worst
  workload, top images) and the rows, filterable by severity, kind, source,
  namespace, workload and image. The image filter accepts the short form
  (`nginx:1.27-alpine`) against the full reference the scanner stores
  (`index.docker.io/library/nginx:1.27-alpine`) — an exact match found nothing
  and "nothing" read as "clean image", which is the question asked before a
  rollback. `cluster: "all"` spans every cluster the caller may read.
- `get_finding_workloads` — workloads ranked by findings, per Security lens
  (vulnerabilities, configuration, permissions, compliance).
- `get_finding_detail` — one finding re-read live from its scanner, degrading
  to the stored row, with the cluster's name — never its UUID — in the error
  when it is unreachable.
- `get_runtime_events` — Falco: counts by priority, the rules that fire most
  and a recent sample. Bounded on purpose (10 rows by default, 25 at most, 10
  useful fields out of ~40, a 24 KB budget): one event is ~1.7 KB and a week of
  them overflowed the tool's cap. Command lines are redacted.

**History.**
- `get_insight_episodes` / `get_insight_episode` — the insight lifecycle from
  2.1: every episode in a window with its status, and one episode whole, with
  its transitions and recurrence.
- `get_operational_episodes` — bursts: many things failing together in a short
  window (a node rotation, pressure, a mass rollout). Kobi's prompt now tells it
  to check bursts **before** blaming a workload: a pod that died with its node
  is not the pod's fault. Bursts report `onsetFrom` / `onsetTo` — when the
  breaking started and stopped — instead of a window stretched by one chronic
  member into weeks.
- `get_recent_deploys` — Deployment rollouts of the last hours (24 h by default,
  up to 168), newest first, with image and age: "what changed just before" is
  the first question of almost every diagnosis. It says what it cannot see
  (rollbacks to an existing revision, StatefulSets, DaemonSets), so an empty
  list does not read as "nothing changed".

**Metrics and capacity.**
- `query_metrics` — PromQL, instant or over a range, confined to the current
  cluster by the store (see §4).
- `get_right_sizing` — the Capacity page's right-sizing, from the same engine
  (see §6).
- `get_workload_metrics` gains **node filesystem**: `metric=filesystem` for a
  Node, from node-exporter when it is installed and from the agent's own
  kubelet stats otherwise (most clusters have no node-exporter). Node-only on
  purpose: attributing a node-wide disk fill to one workload is the error the
  lane exists to prevent.
- `get_coverage` — what KubeBolt can and cannot see on this cluster: which
  metric sources are active, which agents are connected and how, and the gaps,
  so "I see no data" is never mistaken for "there is nothing".

**Across clusters.**
- `get_fleet_summary` — insight counts and the worst cluster across every
  cluster the caller may read.
- `list_clusters` — the caller's clusters and whether each is reachable; it now
  answers with no cluster connected, which is exactly when a client asks.
- `offer_cluster_switch` (chat only) — when the answer lives in another
  cluster, Kobi offers a one-click card: it switches, starts a clean
  conversation there, and asks the original question again, prefixed with what
  was already established. It checks the target is connected before offering,
  so there is no dead card.

## 2. Investigations that hold up

**Summaries, not the screen.** `list_resources` and `get_cluster_overview`
returned what the UI renders. Fourteen `kube-system` pods came to 41 KB —
annotations, volumes, env, full container specs, every condition — and were
cut at the 32 KB tool cap, after which Kobi counted 18 pods where there were 14.
Now:

- each `list_resources` row keeps status, readiness, restarts, node, labels
  (selectors are matched against them), the owner as `Kind/name`, each
  container's image, state, **last termination** (the `OOMKilled` behind a
  CrashLoop) and resources, and only the conditions that are **not** healthy,
  with their message. Completed Job pods carry none — they are not Ready by
  design. Annotations, volumes, env, ports and probes are left to
  `get_resource_detail`, and the result says so. 41 KB → 15 KB.
- `get_cluster_overview` keeps counts, capacity and health whole, the 10 most
  recent Warning events (`get_events` has the rest), and per namespace only the
  workloads that need attention — fewer ready replicas than desired, or a pod
  not ready — plus those scaled to zero. 38 KB → 10 KB.
- The REST API and the UI are unchanged; this is what Kobi reads.

**Node rows carry `internalIP` and `podCIDR`.** Kobi's prompt classifies a
dependency's address as in-cluster only when it matches a node's InternalIP or
falls inside its pod range — and the node list never carried either. It does
now, so "is 172.18.0.4 one of our nodes?" is answered from the list.

**Resource types as Kubernetes names them.** Per-resource tools (`describe`,
`detail`, `yaml`) accepted only the plural key (`pods`); models pass `pod`,
`Pod`, `deployment`, and most describe calls failed on it. Any case, singular or
plural, is accepted now.

**Deployment conditions carry `lastUpdateTime`.** A `Progressing` condition
stays True rollout after rollout, so its transition time dates an old rollout
while its message names the current ReplicaSet — a pair that dated a rollout 47
minutes before it existed. Both times are returned now.

**Optional resources that are not installed say so.** `list_resources` on a
CRD that is not installed (cert-manager, VPA, Argo CD, Cilium policies) answers
"not installed" instead of "forbidden", which sent operators after an RBAC grant
for an API that does not exist.

## 3. Kobi for your own LLM client

**"MCP only" API tokens.** *Create API token* offers **MCP only (read-only
tools)**: the key reaches `/api/v1/mcp` and nothing else, its role is fixed to
viewer — on the server too, whatever the request asks — and it expires in 90
days unless you change it. Until now the only way to reach MCP from the form was
**Everything**, which handed the whole API to a key that only needed read-only
tools.

**Per-token cluster lists.** Every API token reads every cluster, or only the
ones ticked for it, editable later from the pencil on its row
(`PATCH /admin/api-tokens/{id}/clusters`). The list is checked before any other
shortcut, on every read path:

- the cluster a request names (`X-KubeBolt-Cluster`), and the cluster a request
  that names none falls back to — which is pinned to the cluster checked, so it
  cannot move mid-conversation;
- everything scoped per cluster: findings, runtime events, insight history,
  bursts, mutes, the shift report, the fleet PromQL path;
- the cluster lists: `GET /clusters`, fleet search, `list_clusters`.

A limited token cannot switch the active cluster or reach organization
administration, and **no API token can create, edit or revoke API tokens** —
credentials are managed by a signed-in admin.

The MCP catalogue leaves out `offer_cluster_switch`: it draws a card only
Kobi's panel can render.

## 4. Security

**Caller-written PromQL is confined by the store.** Every PromQL a caller writes
— `/metrics/query`, `/metrics/query_range`, the admin metrics queries and
`query_metrics` — now reaches VictoriaMetrics with one server-built
`extra_filters[]` the store enforces on the parsed query. The text rewriter
that pinned the cluster before was a regex over the query, and it left three
shapes unscoped: bare metric names outside its prefix list (`up`,
`process_*`), selectors with a decoy label containing the reserved name
(`{x_cluster_id=""}`), and MetricsQL or-filters, where the pin bound only the
first branch. On a VictoriaMetrics shared by several clusters, those read the
other clusters' series. The rewriter still runs as a second layer.

**The chat runs its tools on the request.** Kobi's chat executed tools on an
empty context, which carries neither the caller nor its scope: the per-cluster
entitlement and a token's cluster list held on `/mcp` and not in the chat. It
now runs them on the request context.

**Tool results are redacted.** Secrets in logs, environment variables, command
lines, `describe` output and events are masked before they reach the model —
the same detectors whether the caller is the chat or an MCP client. Hex-only
runs such as trace IDs are left alone.

**History follows the caller's clusters.** Insight episodes (list and detail),
bursts, mutes (list, create and delete) and the shift report answer only for
clusters the caller may read. A caller limited to some clusters asking for
"all clusters" is served cluster by cluster, not by filtering an organization
page that could come back full of other clusters' rows and empty for theirs.

## 5. Insights

**Only malfunctions form a burst.** An expectation (a policy orphan, a PDB that
matches nothing, an under-requested resource) describes how the cluster is
configured, not something that happened at an hour; the evaluation tick stamped
them all at once and the clusterer read "140 things broke in the same minute".
Replayed over a real history: 309 bursts → 70, and the share classified by
kind (node rotation, pressure, mass rollout) 22% → 64%.

**The burst view.** `/insights?view=bursts`, a third segment beside Active and
History, with the window in the URL so a burst can be linked. Kobi's burst card
links to the window it actually looked at.

**Evidence.** Rules can now hand over the structured facts they saw instead of
flattening them into a sentence; the first, *Service has no ready endpoints*,
records the owner (and its absence, which is usually the finding: a Service
that outlives its workload never had one), the selector, the endpoint split,
when the Service was created and its operator labels.

## 6. Capacity

**Right-sizing moves to the backend.** The rules — NEAR-LIMIT, OVER-PROV,
NO-SPECS, with the same thresholds, floors and headroom as before — lived in
the browser, where a Kobi tool copying them would drift from the screen.
`GET /right-sizing` now computes them from the same 7-day P95 queries, pinned to
the cluster by the server and cached 5 minutes; the Capacity panel and
`get_right_sizing` read the same result. CPU and memory suggestions now round
separately: rounding by magnitude treated a CPU suggestion above one core as
bytes.

## 7. Kobi's cost, models and panel

**An hour of prompt cache.** Measured on real sessions, 68–89% of a session's
cost was cache *writes*: the ~27k-token static prefix (system prompt and tool
definitions) was re-written at 12.5× the read price because the API's 5-minute
entry expired between questions asked at a human pace. It now stays cached for
an hour (`KUBEBOLT_AI_CACHE_TTL`, default `1h`; Helm `copilot.cacheTtl`; `5m`
restores the API default), which pays for itself from the second question in
the hour; a truly one-shot install costs about 60% more per question, which is
what `5m` is for. The conversation is also
cached between tool rounds. Anthropic only.

**Models.** Claude Opus 5.5 and GPT-6 Sol / Luna join the catalogue, priced
from the providers' pages (Opus 5.5 reads cache at 0.05×, not the 0.1× of the
rest of the Claude line). The GPT-5.6 line no longer fails with HTTP 400 on
every turn that carries tools: its server-side reasoning default is
incompatible with function tools on chat completions, so KubeBolt turns
reasoning off for those turns only — as a fallback model it was failing exactly
during an outage.

**The panel.**
- It shows the model that actually runs: the Copilot configuration is read once
  the session is proven, not anonymously before it.
- Tables no longer squeeze headers to one letter per line: they fill the panel
  and scroll when they must, and words stay whole.
- A conversation belongs to the cluster it started on; switching starts a new
  one and the history names the cluster.

## 8. Web

- **Sign-in pages** rebuilt: See. Understand. Operate., one card, a cluster
  console that narrates a node healing, an entrance per form, scaling on wide
  monitors and scrolling on phones. The version pill links to this project's
  releases.
- **The top bar and the Overview KPI cards size to their own width**, not the
  window's: with Kobi's panel docked they no longer break "Cluster Map" onto two
  lines or clip their legends.
- **Home's fleet breakdown** spans the row when there is a single group.

Security patch, same v1.0 metric/label schema — drop-in within 1.x:

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt --version 2.2.0
helm upgrade kubebolt-agent oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt-agent --version 1.4.1
```

Pass your values file explicitly rather than `--reuse-values`, so new defaults
(`copilot.cacheTtl`) are picked up. Nothing to migrate. Existing API tokens keep
reading every cluster; if an MCP host was set up with an **Everything** token,
replace it with an **MCP only** one.

## Behaviour changes to know about

- `list_resources` and `get_cluster_overview` return summaries to Kobi and MCP
  clients; the REST endpoints and the UI are unchanged.
- API tokens can no longer call `/api/v1/admin/api-tokens`.
- A token whose only scope is `/api/v1/mcp` is stored as viewer.
- `/mcp` no longer lists `offer_cluster_switch`.
- Caller-written PromQL that read series from other clusters now returns only
  the current cluster's.

## Verification

On kind with two clusters: create an MCP-only key limited to one of them and
check that `list_clusters` names only that one, that a header naming the other
answers 403, that a request with no header lands on the allowed cluster, and
that `query_metrics` returns the same counts with decoy labels, or-filters and
bare names as without them. Ask Kobi how many pods run in `kube-system` and
compare with kubectl.
