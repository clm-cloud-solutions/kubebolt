# KubeBolt 2.6.4 — a large cluster connects through its agent, and a burst of insights is one notification

Drop-in over 2.6.3. No schema change, no migration, no chart change, and the
agent stays on **1.4.9**.

## A large cluster connects through its agent

Two kinds of request sent the API server `resourceVersion=0`. The API server
answers those from its watch cache and ignores the page size, so each came back
as a whole collection in one body. On an agent-connected cluster that body goes
through the agent. With thousands of ReplicaSets it is tens of MB: enough to
exhaust the agent's memory and to run past the tunnel's per-request timeout.

- **The informer cache audit** (every 5 minutes) asks for one object and reads
  the count from `remainingItemCount`: a few KB per type instead of every Pod,
  Deployment and ReplicaSet. When the server does not report that count, it
  skips the pass instead of reporting a false divergence.
- **The informers' initial LIST** (every connect) arrives in pages of 500
  objects. Watches are unchanged.

On a test cluster with 5,600 ReplicaSets the agent now stays at about 64 MiB
through the connect.

## A burst of insights is one notification

A cluster's first evaluation, a reconnect after its episodes expired, or a
node taking dozens of workloads down used to send one message per insight on
every channel.

- **One summary instead.** When a cluster opens 5 or more insights within 60
  seconds, Slack, Discord and instant email get one summary once the cluster
  has been quiet for 30 seconds. A burst that does not settle gets a partial
  *still going* summary every 5 minutes at most.
- **What the summary holds.** The count by severity, every critical insight
  named (up to 10, with a link) and every rule with its count and most affected
  namespaces. The first insights, sent before the burst was clear, are counted
  and marked.
- **Below the threshold** every insight is still sent the moment it is
  detected.
- **Digests.** An hourly or daily digest with more than 20 insights is
  summarised the same way.
- **Always on.** Summaries cannot be turned off.
  `KUBEBOLT_NOTIFICATIONS_BURST_*` and `KUBEBOLT_NOTIFICATIONS_DIGEST_LIST_LIMIT`
  set the baseline, and Settings › Notifications › *Summaries* moves it within
  fixed ranges.

The Notifications settings page is laid out by what each setting does: what is
sent on the left, where it goes on the right.

## Namespaces on a large cluster

- The Overview's *Workloads by namespace* shows the first 12 namespaces, the
  ones that need attention first, and *Show all* for the rest. The button says
  when hidden namespaces still need attention.
- The Namespaces page used to show 50 namespaces and say "50 total". It now
  pages 50 at a time, counts them all and filters by name.

## Fixes and security

- **The Helm release view** hides a release's values and rendered manifest the
  way the YAML viewer hides the objects themselves: Secret values, and
  credentials in the values found by name and shape.
- **The pod file browser** requires the Editor role, like the terminal.
- **`set-env` records** in the audit trail and the API log keep the names and
  sources of the variables changed, never their values. Older records are
  cleaned at startup.
- **Runtime events** are filtered for credentials when stored and when read.
- **An Argo CD Application's** Helm values, parameters and plugin environment
  are hidden in the YAML view, in describe and to Kobi. Describe also hides the
  ConfigMap values the YAML view hides.
- **Saving a secret store from the YAML editor** keeps its inline credential
  instead of writing the placeholder back over it.
- **A cluster switch** to the cluster already active no longer closes the
  port-forwards open on it. Access-audit records carry the cluster the access
  reached.

## Upgrading

```bash
helm upgrade kubebolt oci://ghcr.io/clm-cloud-solutions/kubebolt/helm/kubebolt \
  --version 2.6.4 -n kubebolt --reset-then-reuse-values
```

Use the namespace you installed into: `helm list -A | grep kubebolt` shows it.
`--reset-then-reuse-values` needs Helm 3.14+; passing your values file (`-f`)
works too. Do not use `--reuse-values`: it keeps the previous chart's defaults,
pinned image tags included. Step by step, what to expect, rollback, and what
each version asks of you when you skip some:
[Upgrade](https://github.com/clm-cloud-solutions/kubebolt/blob/main/deploy/helm/kubebolt/README.md#upgrade).

Nothing in 2.6.4 asks anything of you. Notifications change behaviour: a burst
of insights now arrives as one summary per channel.

The agent stays on 1.4.9: there is no agent release with 2.6.4. On a cluster
with thousands of workloads, its default 128Mi memory limit may still be tight.
Raise it on the agent's release with `--set resources.limits.memory=512Mi`.
