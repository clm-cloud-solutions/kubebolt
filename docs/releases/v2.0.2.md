## 1. A Monitor tab for PVCs

The kubelet has always reported `kubelet_volume_stats_*` — used and capacity
bytes, inode counts — labelled by claim and namespace, and nothing in the product
read them. The cluster card counted PVCs; **how full** any of them was could only
be answered by exec'ing into a pod and running `df`.

Four charts on the PVC detail page: space used in bytes (used *and* capacity as
series, so an expanded volume steps up mid-chart instead of being flattened to a
single current reading), space used %, inodes %, inodes count — with thresholds
at 85 % ("plan an expansion") and 95 % ("running out"), visible by default.

**Inodes get equal billing with space on purpose.** A volume can be 3 % full and
fail every write because inodes ran out — writes error, `df` shows room, and
nothing else in the product would have shown the cause.

Every query aggregates with `max by (persistentvolumeclaim)` before dividing.
PromQL refuses to divide when either side has more than one series per group,
and a PVC produces several for two independent reasons: a cluster running its
own kube-prometheus-stack scrapes the same kubelet the agent already reports,
and an RWX volume mounted by several pods emits one series per pod. `max` rather
than `avg`: a fullness reading should err toward the fuller answer.

`pickScale` gained a `count` unit — inode counts rendered raw (`4194304`), now
`4.19 M`; the k threshold sits at 10 000 so `1500` stays readable.

> **Testing note:** kind's default StorageClass provisions hostPath PVs, and the
> kubelet has no metrics provider for hostPath, so the tab stays empty there and
> it is not the UI's fault. `csi-driver-host-path` makes the series appear; real
> cloud CSI drivers report correctly.

## 2. The Go security wave

Six HIGH Go stdlib CVEs were published mid-cycle (`encoding/asn1`, `net/http`
unencrypted HTTP/2, `html/template` XSS, `encoding/xml`, `net/url`,
`crypto/tls`). KubeBolt's own images are clean: every OSS build path has run Go
1.26.6 since 1.23.2. VictoriaMetrics and vmagent `v1.148.0-scratch` carry all
six plus the two `x/net` ones — the 8 entries in `.trivyignore-thirdparty`,
owner, exposure and **remove-by 2026-09-15** unchanged. `v1.149.0-scratch` is
built with the same Go and buys nothing. If the list grows again without VM
publishing a rebuild, the question stops being "renew the waiver?" and becomes
whether a vendored binary that ships months behind the Go security line is still
the right dependency.
