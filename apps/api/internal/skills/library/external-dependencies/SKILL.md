---
name: external-dependencies
audience: kobi
description: Following a failure out of the workload — a Service with no selector or of type ExternalName, a URL or IP in the workload's env, an address of another cluster of the organization, a managed cloud service behind it. Load it before you call a dependency missing, external or the cause, before you blame the network for a connection failure, and before your first cloud connector call.
---
**Do not infer "missing workload" from a zero pod count.** Before concluding a workload is absent because a namespace has 0 pods / 0 Deployments, inspect the Service that fronts it. A **selectorless** Service (no .spec.selector) backed by manual Endpoints / EndpointSlice, or a Service of type ExternalName, is a **deliberate external dependency** — a database, cache, or API running outside the cluster. The fix for an unreachable external dependency is to **restore or repair that external endpoint** (the host it points at, the network path, credentials). It is NEVER to deploy an in-cluster workload to "replace" it, nor to rewrite the Service to use a selector — that would silently abandon the real backing store. When a service-no-endpoints situation involves a selectorless Service, say "the external endpoint X is unreachable", not "the selector matches no pods".

**Identify any IP before you reason about it — never guess that an address is a node.** To call an Endpoints / EndpointSlice address a node IP, you MUST have listed nodes (list_resources type=nodes) THIS turn and matched the address to a node's InternalIP — do not name a node from memory or inference. An address that is neither a listed node's InternalIP nor inside a pod CIDR is an **external** target; name it as external. **Contradiction guard:** a node you can read through the API is, by definition, reachable by the control plane — so if a connectivity probe reports a "node" as entirely unreachable on every port, your IP labeling is wrong, not the cluster network. **Evidence hierarchy:** endpoint / Service / readiness evidence outweighs a single connectivity probe to a possibly-misidentified target; when a one-off probe (e.g. nc) seems to contradict a root cause you already established from endpoints and logs, re-verify the probe's target before overturning the conclusion — a probe to a stopped external host returns "unreachable" on every port, which confirms the dependency is down, it does NOT indicate a cluster networking fault.

**When there is no Service fronting the dependency at all**, it may be wired as a raw URL/IP in the failing workload's own config (an env var or arg, e.g. ORDERS_URL=http://1.2.3.4:8080, or a hostname). There is no Service or Endpoints to inspect and the namespace legitimately has 0 of that workload — do NOT conclude it is missing and must be created. Read the failing workload's YAML (get_resource_yaml), find the dependency target in its env/args, and classify that target the same way: an IP that is neither a listed node's InternalIP (list_resources type=nodes) nor inside a node's pod CIDR is external; a hostname in the cluster domain (.svc.cluster.local) names a Service: in-cluster unless that Service is ExternalName or selectorless, so read it before you classify the target (get_external_connections follows it when the flows do not already show the dependency); any other FQDN is external. A dependency's locality is decided by its address, not by whether a Service fronts it — an external URL in an env var is a deliberate external dependency, same as a selectorless Service, and the fix is to restore/repoint that endpoint, never to create a workload in this cluster. To call an IP in-cluster you MUST call list_resources(type=nodes) and match the target EXACTLY to a node's InternalIP — being in the same private/docker subnet as a node (another 172.x address, or a NodePort target you have not confirmed belongs to THIS cluster's node) does NOT make it that node. If the target IP is not an exact InternalIP of a listed node and not inside a listed node's spec.podCIDR, it is external; when unsure, external.

**An external address may belong to another cluster of this organization.** When get_external_connections gives a destination or dependency host an inFleet that names another cluster, that address is a Service, Ingress or Gateway there: do not call it unattributable. When the failing calls go to it (errors, timeouts, 5xx or drops toward that address), the failure is that workload's — offer the switch with offer_cluster_switch to its inFleet.clusterContext, with a question that names what to investigate there, since the other cluster does not run the caller: the operator's words first, then the symptom, the caller and the cluster it runs in, and every workload there the symptom may come from, as namespace/name from their inFleet rows. In established, put the evidence: what you measured and the addresses called. An inFleet with sameCluster true is a workload of this cluster reached through its own external address: follow it here.

**Connection failures — diagnose down the dependency graph before blaming the network.** When a flow fails with a connection error (connection refused, host unreachable, EPERM / "operation not permitted", timeout) or an upstream 5xx, diagnose down the Kubernetes dependency graph before invoking any network-layer cause:

1. **Destination Service endpoints first.** Does the target Service have *ready* endpoints? (get_resource_detail on the Service, or the service-no-endpoints insight.) A connection failure to a Service with zero ready endpoints is caused by the missing backends — on every CNI — not by a policy. Most common cause, cheapest to confirm.
2. **Then backing-pod readiness.** Empty endpoints means the pods are NotReady or absent. Read their readiness probe + logs to find why, and follow the chain (e.g. web → api → db) to the real failure.
3. **The policy / network layer last, and only with evidence.** Consider a NetworkPolicy or any CNI-specific policy CRD (CiliumNetworkPolicy, Calico NetworkPolicy / GlobalNetworkPolicy, or a managed-CNI equivalent) ONLY after the destination is confirmed to have healthy endpoints AND you have read a specific policy whose rules deny *this* flow. The absence of one policy type is never evidence another is blocking. A policy that only restricts ingress does not explain an egress failure; an allow / observability policy denies nothing. Cite the policy and the matching rule, or do not claim it.

**A managed cloud service behind it** (the organization's cloud connectors):

1. Cluster evidence first: establish what fails and how from logs, events, readiness and endpoints. If the cause is inside the cluster, stop there — do not go outside.
2. Call get_external_connections for the failing namespace and workload. It lists the external endpoints the workload actually talks to, already classified: provider, service, resource name, region, and the connector tools to start with.
3. Follow the classification. Use a connector only for a destination whose connectorEnabled is true, starting with its firstTools. Skip infrastructure destinations (metadata service, cloud DNS, control plane): they are plumbing, not the dependency. Before the first AWS call, load_skill aws-investigation.
4. An activity log covers the one resource it was read for. An empty one for the dependency or for the cluster's own resource says that resource did not change, not that the cloud did not. The cluster's own network (on AKS, the network security group, load balancer, NAT gateway and public IPs in the resource group get_external_connections names in clusterNetwork) filters both ways: requests coming in through a cloud load balancer, and connections going out from the pods to a cloud dependency. Each of those resources records its changes, a rule written into the network security group included, in its own activity log. When a dependency is up and unchanged but connections from the pods time out, or a caller cannot get through to a cloud load balancer, list that group and read the activity log of each network resource on the path, and say which ones you read. Take the group's name from clusterNetwork: never list the whole account to find it. On EKS, clusterNetwork lists the node instances instead: their security groups and their subnets' network ACLs and route tables are that network, and CloudTrail records each change under that group's, ACL's or table's id.
5. A load balancer's health probes come in through an allow rule of their own (on Azure, AzureLoadBalancer), so healthy backends and full probe availability do not show that client traffic gets through: a rule that drops traffic from the Internet leaves the probes green. Requests reaching the backend's logs do.
